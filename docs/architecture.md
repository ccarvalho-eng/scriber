# Architecture and reproducibility

Scriber separates source discovery, parsing, layout, packaging, validation, and orchestration so retailer rules do not leak into manuscript content.

```text
book.toml + ordered Markdown + optional cover panels
                    |
             parse and classify
                    |
        +-----------+-----------+
        |                       |
 iterative print layout    reflowable EPUB
        |                       |
 final page count          EPUB package checks
        |
 gutter + spine + cover template/assembly
        +-----------+-----------+
                    |
   release validation, proof report, and manifest
```

## Stable pagination

The PDF renderer repeats layout until the table of contents, section page map, page count, and page-count-dependent inside margin stop changing. It rejects a build if pagination does not stabilize within the bounded pass count.

## Reproducible outputs

The edition date is the canonical build timestamp. EPUB entries use fixed timestamps, permissions, ordering, and compression. PDF canvases use invariant identifiers and timestamps. Publication manifests avoid wall-clock values and contain checksums for every deliverable.

Reproducibility means identical supported inputs and tool versions are intended to produce identical deliverables. The manifest records the profile version and its primary retailer source, which are needed to interpret the geometry and limits. Changes in Python or rendering dependencies may still change output, so released editions should retain their lockfile and manifest.

## Trust boundaries

Book paths are constrained to the book root. ZIP entries are generated by Scriber with fixed names. External validators receive only the built EPUB path and their output is treated as diagnostic text. Scriber does not upload manuscripts or contact retailer services.
